## 1. PARTS ARE CHRISTENED BY DEPLOYMENT
- The selector reads **"UNASSIGNED PART"** until the part's first
  assignment to the play grid (via either side's row selectors) —
  at which moment it becomes **PART 1** (then 2, 3… in deployment
  order). The workshop holds a question; the stage confers the
  name.
- **At that moment, an "ADD PART" button GLOWS** near the selector
  (the invitation grammar: the next question becomes askable only
  once the current one has landed).

## 2. PART-OWNED I/O, BOTH SIDES, LIVE (supersedes the asymmetry)
- **On any part, PLAY THIS MACHINE and PLAY THE STAGING GRID share
  the part's RECEIVERS and EMITTERS across all cells and colours —
  change everything once.** The build column's INPUT and OUTPUT
  chips edit THE PART; every colour follows live.
- **THE EXCEPTION LIVES IN THE CHAIN**: a processor-level output
  override (TO-ALT, dest settings, PING and kin) stands apart from
  the part default. Overrides are IN-PROCESSOR ONLY — never a
  colour property. (This keeps the alt-family whole: TO-ALT *is*
  the override mechanism, exactly where it always lived.)
- §5's "machine owns the wire" is SUPERSEDED; the soft-default
  clause dies with it.

## 3. A NEW PART EXPECTS NEW CHOICES
On ADD PART: I/O and chain arrive UNSET/fresh — the user is
expected to choose new emitters, processors, etc. (supersedes the
inherit-from-previous lean; choosing anew is the point of a new
part). The piano/door pick, the cast, the build — all begin clean;
staging empty; the previous part retains its workshop.

## The lifecycle, one line
Unassigned → built → staged → deployed (christened PART n; ADD
PART glows) → the next question opens fresh.
— design-side Claude

## 4. TERMINOLOGY (Paul, 2026-08-12 — the handles renamed)
- **PLAY THIS MIDI CHAIN** (né machine). Paul's ruling over my
  trim: "MIDI chain" is the HOST's native vocabulary — AUM users
  already build MIDI chains in channel strips, so the full term
  buys recognition at first contact, which outranks in-app
  redundancy. The see-it-name-it bonus stands: the button sits
  above the column whose foot draws the literal chain.
- **PLAY THIS PART** (né the staging grid) — musician-true,
  teaches the part concept, agrees with the christening lifecycle
  (it auditions the unassigned part). Post-deployment ambiguity is
  the audition-mode toggle's job, unchanged.
- **START/STOP THE PLAY GRID** stays — the broken parallelism is
  honest (two auditions and a transport).
- **The trio now reads as ZOOM LEVELS**: chain → part → piece.
  One machine, one question, the whole performance — the page's
  hierarchy taught by its three biggest buttons.
- Harmonisation ripple: where prose/UI says "machinery," prefer
  "the MIDI chain" at first-contact surfaces ("the chain" as
  shorthand once inside) (the flow diagram = the chain; colours
  stay colours). Manual lines update at ship.
