What changes

From a loop browser to a session tape

You asked for three things: replay anything from the start of the session onwards, export several bits you like rather than one range, and a screen that looks designed rather than written. Reading the code and driving the real app turned up twelve problems standing in the way (they are in Docs/pending-tasks.md as REEL-1 to REEL-12). Most of them share one cause: the reel is built around “passes”, a 64-slot ring of 16-beat loops, not around time.

Other shapes

Tall, small, and empty

The layout is one function of the window size, with three shapes. Wide is the one above. Tall stacks the same pieces. Small, for a plug-in window inside AUM, drops the tape strip and lets you select on the overview directly; the keeps tray collapses into one button. The empty state is drawn, not explained.

Fewer words

What the text was doing, and what replaces it

The current screen feels written rather than designed for a reason you can count. It explains itself in a paragraph, uses the code’s vocabulary (pass, extend, emitter), shows the same grey square over and over, and paints notes grey on a cyan chrome that belongs to no other screen. The redesign draws the music and lets direct manipulation carry the instructions.

Whole session

The whole session is affordable

Today’s tape is 64 slots of 8,192 sixteen-byte events: a fixed 8 MiB however little is played. That is why it holds so few passes. A real pass is a few hundred events. I took the note counts from the 26 test documents the allocation audit already plays (the factory presets plus the other note sources) and worked out what a continuous tape would cost.

149 Bper beat on average, per output. 513 B per beat for the densest preset (Arpeggio Ladder).
8 MiBstays the in-memory budget, same as today. Older stretches live in a file and are read back when you scroll to them.
225 KiBis the per-bar summary for eight hours at 120 BPM. The overview draws from that alone, without reading a single note.

How the tape is stored

  • Append-only, in chunks of about 64 KiB, on a session clock of 1/960 beat that starts at the first play.
  • One 8-byte record per event: time, note, velocity, output, and which of the four lanes played it.
  • A tempo map alongside, so exports carry the tempo each bar was played at.
  • A small summary per bar (notes per lane, pitch range, a fingerprint) for the overview and repeat brackets.

How it stays safe on the audio thread

  • The audio thread only writes into a chunk. Chunks come from a pool the main thread keeps topped up; if it ever runs dry the event is counted and dropped, never allocated. The allocation audit stays at zero.
  • While you listen back, the engine keeps generating into a silent tap instead of being skipped, which is why recording never pauses and live can resume in time.
  • Older chunks are written to a file in the app’s own folder, so a relaunch or a crash keeps the session.
The plan

Five phases, each shippable

The order is real: the tape has to exist before replay can use it, and the screen needs both. Phase 0 is small and lands first because it stops files being overwritten today. After phase 1 the old screen keeps working through a thin adapter, so the app is never left half-converted. Sizes are relative: S is hours, M a few days, L a week or more.

Phase0

Stop the damage in today’s reel

Nothing is overwritten and nothing fails silently, before any redesign.

Changes

  • Export names say what is inside: Fourfold · bars 97–104 · A · 14-52-07.mid. A pure, tested function that phase 4 reuses.
  • Save is unavailable, with one line of reason, when nothing is selected or the chosen output has no notes (each output shows its note count).
  • A one-line notice when older passes have dropped off the tape.

How we will know

  • Unit tests for naming: collisions, odd characters, ranges.
  • Tap test: save twice, find two files in Reel exports.
  • Tap tests for both disabled states.

Phase1

The session tape

Everything played from the first play is on tape, and stays there while you listen back.

Changes

  • New SessionTape in Fourfold/Engine replaces the 64-slot ring: chunked, 8-byte events tagged with output and lane, session clock, tempo map, per-bar summaries.
  • The audio thread appends into pre-allocated chunks; the main thread tops the pool up (lock-free hand-off).
  • Replay stops skipping the engine: it keeps running into a silent recording tap.
  • In-memory budget 8 MiB; older chunks spill to a file; the session survives relaunch.
  • The old browser reads the tape through an adapter (16-beat slices) so nothing breaks in between.

How we will know

  • Golden sound check identical: the live path is untouched.
  • run.sh --alloc still zero, with a new scenario that records while replaying.
  • A differential test: the same pass through the old deck and the new tape exports identical bytes.
  • Four simulated hours in a unit test, with a memory ceiling.
  • Soak with random start and stop of replay: no stuck notes. Relaunch test.

Phase2

Replay from anywhere, onward

Pick a bar, press play, hear the session from there, and land back on live when it catches up.

Changes

  • The replay position is the host beat minus an anchor (derived, nothing accumulated), played through the same output path.
  • Three modes: from here onward then back to live; loop the selection; back to live now.
  • The hand-back flushes tape notes and unmutes the engine, which was already running, so live resumes in time.
  • Stopping the transport returns to live, as today. The UI is told whether it is hearing LIVE or TAPE.

How we will know

  • Sample-accuracy test: replayed events land at the same offsets as recorded, at buffer sizes 64 to 4096, across stop, start and a tempo change.
  • Soak extended with random seek, play and stop.
  • Unit tests for the hand-back edge: no orphan note-offs, no stuck note.

Phase3

The new reel screen

The screen above, in any orientation and window size, with no instruction text, readable by VoiceOver.

Changes

  • FourfoldReel.swift rewritten: overview, tape, close-up, transport, keeps tray. Canvas drawing, iOS 15 safe.
  • A pure reelLayout(size:) with the three shapes and floors, and pure selection, zoom and snap maths.
  • Lane colours from the lane tag; repeat brackets from the bar fingerprints (replaces Remove duplicates).
  • A drawn empty state; the rotate prompt is deleted.
  • VoiceOver: the selection start and length are adjustable, play, keep and export are actions, keeps are a list, the close-up has a spoken summary.

How we will know

  • Layout fuzz from 480 × 320 up to a 13-inch iPad in all four orientations.
  • Screenshots on all six iPad simulators (the existing harness), looked at, not just taken.
  • The reel added to the accessibility audit and the tap tests.
  • Frame rate with an 8-hour tape: simulator numbers are indicative only; a device check is owed.

Phase4

Keep and export

Mark what you like while you play; export several keeps in one go.

Changes

  • A keep is a range on the tape with an automatic name, stored with the session.
  • Ways to keep: the star in the reel, a star in the standalone transport bar, a long-press on the header reel icon, and an automation parameter so AUM or a footswitch can trigger it.
  • Grab length for the quick keep: 2, 4, 8, 16 or 32 bars (default 8).
  • Export: one file per keep or joined; mix, per output or per lane; a real tempo track; a new file name each time; a confirmation with Share and Show in Files. Dragging a chip out as a file is a stretch goal.

How we will know

  • A recorded fixture exported, parsed back and compared note for note.
  • Naming collision tests; tap tests for keep, tick, export.
  • A check in AUM on a device: the parameter is mappable, the file gets out through the share sheet.
  • Privacy manifest re-checked: reading file dates or free disk space needs a declared reason.

Decisions

Five calls that are yours

1. What is “the session”, and how long is it kept?

Changes phase 1.

Recommendfrom first play, kept on disk

The session starts at the first play after launch, survives relaunch, and ends when you press New session (with a confirmation, because it deletes the tape). Cap at 24 hours with a visible warning at 80%. Say if you would rather it reset on every launch.

2. When you replay, do you hear tape instead of live, or on top of it?

Changes phase 2.

Recommendinstead of

This is today’s behaviour and avoids doubled notes into one synth. The engine keeps running underneath, so a later Layer switch is cheap if you want it.

3. How do you keep something while playing?

Changes phase 4.

Recommendstar, long-press, parameter

The star in the reel and in the app’s transport bar, a long-press on the header reel icon (the header has no spare width for another button), and an automation parameter so a foot switch or controller can trigger it through AUM. Default grab is the last 8 bars. Does a hands-free trigger matter to you? If you play keys, it probably does.

4. Bars or passes?

Changes phases 1 and 3.

Recommendbars

A pass is 16 beats counted from the start of the transport, so a phrase that begins mid-pass gets split. Bars follow the host’s time signature and are what you count in. Passes disappear from the screen.

5. Is the share sheet enough for getting files out of AUM?

Affects phase 4.

Recommendyes for now

Inside AUM the plug-in’s folder is hidden, so files leave only through Share. In the standalone app they also land in Files. Sharing the folder between the two would need an App Group; I would leave that until you ask.

Risks

What could go wrong, and what I have not checked

Risks

  • Audio thread. A mistake in the chunk hand-off could allocate or block. The allocation audit and the soak are the gates; neither lands without passing.
  • Engine order. Running the engine during replay changes the render sequence in the Kernel. The golden sound check covers the live path; replay scenarios are added to it.
  • Plug-in memory. An AUv3 extension has a hard, undocumented memory ceiling. The 8 MiB budget is deliberately no larger than today’s tape.
  • One copy only. This lands in Fourfold/Engine. The frozen 8x8 State reel keeps its old behaviour.
  • Overlap. Another instance is working on the page’s small-window fallback. The reel’s small layout should share its minimum size.
  • iOS 15. No iOS 16 SwiftUI in the new screen. Nothing has run on iOS 15 yet.

Not verified

  • Nothing is built. The mockups are illustrations; their notes are generated, not captured.
  • The storage figures come from note counts in the 26 audit scenarios, not from a real long session.
  • I have not heard any of this, and I have not measured how much memory an AUv3 extension may use on an older iPad.
  • No one but me has looked at the layout. Real hands on a real iPad may want different hit sizes or a different zoom.
  • Whether eight bars is the right default grab, and whether a footswitch matters, are guesses until you say.
